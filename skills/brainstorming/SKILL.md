# 头脑风暴:从想法到设计

在写任何实现代码前,把模糊想法变成清晰设计。判断是否需要此 skill:**"我对要做什么、为什么做、做成什么样,是否清晰到可以直接写代码?"** —— 不清晰就用,清晰就直接做。

## 何时用

- 需求模糊或方案有多种可能时
- 涉及多模块、架构决策
- 请求描述了多个独立子系统,需要先分解

## 何时不用

- 目标完全明确、单文件小改 → 直接做
- 纯调查/排查 → 用 subagent 扩展(如 scout)或 bug-* 技能,不需要设计
- 用户已给完整 spec → 直接进入实现

## 流程(弹性,非仪式)

1. **先探索项目上下文**:看文件、文档、近期 commit。带着理解再问问题,不从零问起。
2. **一次一个问题**:别一次抛多个。多选题优先于开放题(用户更好答)。
3. **大请求先分解**:如果请求描述了多个独立子系统(如"建一个带聊天/文件/计费/分析的平台"),先帮用户分解成子项目——每个子项目走自己的 设计→实现 循环。别在一个 spec 里塞一整个平台。
4. **提 2-3 个方案**:带 trade-off,先给推荐项和理由。别第一个想到的就上手。
5. **分段呈现设计**:每段复杂度决定篇幅(简单几句,复杂 200-300 字)。每段后确认"这样对吗",不对就回去改。
6. **为隔离与清晰而设计**:拆成职责单一、接口清晰、可独立理解的单元。每个单元能回答"做什么/怎么用/依赖什么"。

## 设计要点

- **YAGNI**:ruthlessly 删掉"将来可能有用"的特性。只在当下需要时设计。
- **探索替代方案**:总有第二种做法,看不到替代方案就谈不上选择了最优的。
- **在已有代码库中**:先遵循现有模式;顺路改进你触碰到的有问题的代码(边界不清、职责纠缠),但不做无关重构——refactor 不在 brainstorming 阶段。
- **边界检验**:一个单元如果"不看内部就无法理解"或"改内部就破坏调用方",它的边界还需要打磨。

## 定稿后

1. **写成 spec 文件**:位置遵循项目约定或用户偏好(默认 `docs/specs/YYYY-MM-DD-<topic>-design.md`)。
2. **Spec 自审**(写完用新鲜眼光扫一遍):
   - **占位符**:有无 TBD/TODO/未完成段?当场补。
   - **内部一致性**:各段是否矛盾?架构和功能描述对得上吗?
   - **范围检查**:单个实现计划放得下吗?放不下 → 分解。
   - **歧义检查**:某条需求能否两种解读?能 → 选一个,写明确。
3. **请用户 review**:spec 写好并自审后,请用户过一遍,确认后再进入实现。

## 与其他框架的关系

- **AGENTS.md §3**:定"设计文档是活文档、禁完整实现代码、条件分支需谨慎"——本 skill 产出物须符合 §3。
- **test-driven-development**:定"实现时怎么保证质量"——本 skill 定稿后,实现阶段走 TDD。

本 skill 不重复上述规则,只负责让设计更扎实。

## 弹性原则

这不是硬流程。判断标准:**"用户和我的理解是否对齐到可以开始实现?"**

- 简单项目:设计可能就几句话,对齐了就开始,别为走流程而走流程。
- 复杂项目:完整走完,每段验证。
- 不给自己设 HARD-GATE:"必须先有完整 spec 才能写代码"是过度僵化——判断何时该实现是 agent 自身职责,本 skill 只负责让设计更扎实。
