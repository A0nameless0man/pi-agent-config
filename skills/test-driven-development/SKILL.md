# 测试驱动开发 (TDD)

## 核心原则

先写一个会失败的测试,**亲眼**看它失败,再写最小的代码让它通过。

**为什么顺序重要**:测试先行回答"应该做什么";代码先行再补测试回答"已经做了什么"——后者被实现带偏,测的往往是实现细节而非需求。

**亲眼看到失败**是关键:它证明测试确实测了东西,而不是 no-op、打错靶、或依赖了已存在的行为。

## Red-Green-Refactor

1. **RED** — 写一个最小的、描述目标行为的测试。运行它。确认它因为"功能不存在"而失败(不是因为拼写错误或 import 缺失)。
2. **GREEN** — 写最小的代码让测试通过。不超出测试范围(YAGNI)。不为"将来可能需要"加参数、加分支、加抽象。
3. **REFACTOR** — 只有测试绿了之后才清理:去重、改名、抽函数。全程保持绿,不加新行为。

循环往复:下一个失败测试 → 下一个特性。

## 何时用 TDD(默认用)

新功能、bug 修复、重构、行为变更——任何有"可验证行为"的代码。

## 何时可以不用 TDD(判断,不是偷懒)

AGENTS.md §3 要求过程保持弹性。TDD 也有合理例外:

- **探索性 spike / 原型**:你在学习领域、验证可行性,不在交付。→ 学到后丢掉探索代码,正式实现走 TDD。
- **配置文件、文档、纯数据**:没有行为可测。
- **一次性脚本、glue code**:测试比代码本身还重时,权衡投入产出。
- **生成代码、脚手架**:生成后再补行为测试。

判断标准:"这段代码有可验证的行为吗?这个行为值得固化成回归保护吗?" 两个都"是" → TDD。任一为否 → 可以跳过,但心里清楚为什么。

## 好测试

- **最小**:一个测试一个行为。名字里有"and"?拆开。
- **清晰**:名字描述行为(`rejects empty email`),不是 `test1`。
- **测行为不测实现**:用真实代码,mock 仅在不可避免时(外部依赖、网络、时间)。mock 一切 = 你在测 mock 不是测代码。

## 为什么测试后补不够

- 测试立刻通过 → 什么都证明不了:可能测错东西、可能测实现细节、可能漏了边界。
- 手动测过所有边界 → ad-hoc,没记录、不可重跑、压力下容易漏。
- 测试先行强制你在实现**前**发现边界;测试后补只验证你**记得**的边界(你记不全)。

## Bug 修复

先写一个复现 bug 的失败测试 → 修复代码 → 测试通过 → 这个 bug 被回归测试永久保护。

不写复现测试就修 bug,同样的 bug 会回来。

## 当测试很难写——这是设计反馈

| 问题 | 往往意味着 |
|---|---|
| 不知怎么测 | 先写出期望的 usage(API),再写断言 |
| 测试太复杂 | 设计太复杂,简化接口 |
| 必须 mock 一切 | 耦合过紧,用依赖注入 |
| setup 巨大 | 抽 helper;还复杂?设计要简化 |

**难测 = 难用**。测试的难度是对设计质量的反馈。

## 纪律与弹性的平衡

TDD 是纪律,不是教条:

- 默认走 TDD,但坦然识别合理例外(见上),不为走仪式而走仪式。
- 警惕 AGENTS.md §3 的告诫:"看起来通过"≠"真正达成"——测试通过不是终点,测试确实捕获了**真实行为**才是。一个永远通过的测试和没有测试一样无效。
- 把"想跳过 TDD"的冲动当信号,自问:这是合理的例外(可验证行为弱/一次性),还是在合理化偷懒(就是不想写测试)?诚实回答即可,不需要仪式化的自我惩罚。
- 测试套件本身是活文档:它随需求演化而增减,不是一旦写下就神圣不可变。
